# AI 推理方案选型与成本测算引擎

> 输入客户推理场景（模型规模、并发量、上下文长度、时延要求），输出卡数配置、
> **显式含 KV Cache 的显存测算**、并行策略建议、**每瓦 Token 吞吐量**、三年 TCO，
> 并装配技术方案书、商务标书技术章节、产品白皮书与四层形态规格书。
>
> **场景为自拟、测算为公开规格驱动的理论推算，非真实业务数据、非实测性能。**

零第三方依赖，`git clone` 后直接跑。

---

## 1. 为什么做这个

推理选型与训练选型是两件不同的事，而绝大多数算力测算工具只做训练口径：

| 环节 | 训练 | 推理 |
|---|---|---|
| 显存瓶颈 | **权重** | 常是 **KV Cache**（长上下文/高并发时） |
| 关键指标 | MFU（模型算力利用率） | **每瓦 Token 吞吐**、每 Token 电费 |
| 并行策略 | TP + PP + DP | TP 或 EP，取决于是否 MoE |
| 成本结构 | 一次性硬件为主 | **电费随运行时间持续累积** |

只算权重会系统性低估显存需求 → 卡数算少了 → 交付时 OOM。
这是推理场景最常见、也最贵的返工。

这个工具做的事：**把「客户这个推理场景要几张卡、每瓦跑多少 Token、
三年电费多少」变成可复算的推导过程**，而不是一个拍脑袋的数字。

## 2. 覆盖哪些能力

| 能力 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| 卡数与显存 | 模型 + 上下文长度 | 卡数、显存构成拆解 | **KV Cache 显式计算**，不是只算权重 |
| 并行策略 | 模型结构 + 卡数 | TP / EP 建议 + 通信代价 | 必须说明**为什么这么切** |
| **每瓦 Token 吞吐** | 配置 + 功耗 + 引擎 | token/s/W | 每个参数可溯源；**占位值显式标注** |
| 三年 TCO | 配置 + 电价 + 利用率 | 分项成本 | **电费单列**；硬件价未查到就列为未计入项 |
| 四层形态校验 | 芯片→板卡→服务器→一体机 | 跨层冲突清单 | 能发现「板卡 6 槽但服务器只有 4 槽」这类断裂 |
| 文档装配 | 以上全部 | 5 类交付物 | 一键生成，含免责声明 |

## 3. 核心设计决策

### 3.1 KV Cache 必须显式算

```
KV Cache = 2(K,V) × 层数 × kv_head 数 × head_dim × (输入+输出 token) × 2 Byte
```

实测对比（`finance_rag` 场景，Qwen2.5-32B，2000+500 tokens）：

```text
权重 61.09 GiB + KV Cache 0.61 GiB = 61.70 GiB → ×1.10 余量 = 67.88 GiB
```

短上下文时 KV 只占 1%，但**上下文拉长或并发上去后，KV 会吃掉大部分显存**。
只算权重的测算在长上下文场景下会明显偏乐观。

### 3.2 TP 与 EP 的通信量差异要有解释

| 维度 | 张量并行（TP） | 专家并行（EP） |
|---|---|---|
| 适用 | 稠密模型（无专家可切） | **MoE 模型** |
| 通信 | 每层 2 次 all-reduce | **仅 MoE 层** 1 次 all-to-all |
| 通信量 | 含 `(cards-1)/cards` 因子，随卡数放大 | 不随卡数线性放大 |
| 代价 | 互联带宽要求高 | **专家负载不均** |

实测（Mixtral-8x7B，8 卡）：TP 1.75 GiB/步 vs EP 0.50 GiB/步，**EP/TP = 0.29**。

> 这个比值依赖「MoE 层占总层数比例」这一假设（占位值 0.25）。
> 该比例是本模块**最敏感的参数** —— 真实 MoE 模型的 FFN/attention 布局各不相同，
> 须按目标模型的实际结构替换。输出里已显式标注这一点。

### 3.3 硬件采购价未查到，就不计入合计

加速卡单价属商业信息，厂商未公开。TCO 输出中该项列入「未计入项」并注明
**「合计不完整」** —— 而不是按 0 元凑出一个看起来完整的总数。

原因很直接：编一个价格算出的 TCO，在客户面前一问就穿帮；
少算一项并说清楚，客户反而知道下一步要补什么。

### 3.4 优化系数不叠加

量化 1.6 / 投机解码 1.8 / 前缀缓存 1.5 / 连续批处理 1.4 ——
四项同时生效时**取最大值而非连乘**。

理由：多项优化作用于不同瓶颈，相乘会严重高估（1.6×1.8×1.5×1.4 = 6.0 倍，
这在任何单卡上都不可能）。取最大值保守但诚实。

## 4. 数据源与合规边界

| 数据 | 来源 | 可信度 |
|---|---|---|
| 模型结构参数 | 公开模型卡（Qwen / DeepSeek / Mistral / Llama） | secondary / official |
| 目标加速卡规格 | 公开报道（国产推理 GPU，未具名） | secondary / **unverified** |
| 竞品规格（A100 / L40S / MI300X） | NVIDIA / AMD 官方 | official |
| 推理引擎能力 | vLLM / TensorRT-LLM / SGLang 官方仓库 | official |
| 场景参数 | **自拟** | — |

> **本项目无任何 `official` 级的目标加速卡数据** —— 厂商官网以产品宣传与技术叙事为主，无参数表。
> S3 与 REX-S 的详细规格标 `unverified`，REX-S 的单卡显存直接标「未查到」，
> 因此测算对它输出 `unknown` 而不是猜一个。

**明确不含**：真实客户名称、合同金额、账号凭据、内部报价、厂商内部测试数据。

## 5. 方法

```
data/scenarios/<场景>.json ─┐
data/models/model_specs.csv ├─> catalog.py ──> 目录（缺列即报错）
data/hardware/*.csv         │
data/frameworks/*.csv      ─┘
                                    │
   sizing.py ── 权重 + KV Cache 显式显存 → 卡数（向上取整到整机）
      │
      ├─ tp_ep.py ──────── 按是否 MoE 推荐 TP/EP + 通信量量级对比
      ├─ token_per_watt.py ┈ 整机 TPS ÷ 整机 TDP = 每瓦 Token 吞吐
      ├─ tco.py ────────── 电费单列 + 每百万 Token 电费
      ├─ form_validator.py ┈ 芯片→板卡→服务器→一体机 跨层一致性校验
      │
      └─ doc_assembler.py ┈ 方案书 / 标书技术章节 / 白皮书 / 规格书 / 理解成本清单
```

## 6. 快速开始

环境：Python 3.10+（验证于 3.12.8 / Windows）。**无需安装任何运行时依赖。**

```bash
# 跑全部场景
python -m src.cli --all

# 指定加速卡与利用率
python -m src.cli --scenario finance_rag --accel S3 --util 0.8

# 竞品规格对照 + 每瓦吞吐推演
python -m src.cli --compare

# 跑测试
pip install pytest
python -m pytest -q
```

输出落在 `output/<场景编号>/`：

| 文件 | 内容 |
|---|---|
| `solution_proposal.md` | 技术方案书：需求约束 / 显存测算 / 配置建议 / 每瓦吞吐 / 三年 TCO / 边界声明 |
| `bid_section.md` | 商务标书技术章节：供货配置 / 性能承诺（含承诺条件）/ 运行成本 / 交付一致性 |
| `whitepaper.md` | 产品白皮书：为什么用每瓦 Token 吞吐做主指标 + 规格对照 + 推演假设 |
| `form_spec.md` | 四层形态技术规格书 + 一致性校验报告 + 字段完整率 |
| `customer_understanding_cost.md` | 客户理解成本清单：客户会问什么、怎么答、哪些说法会丢订单 |
| `result.json` | 全量结构化结果 |

```text
$ python -m pytest -q

$ python -m src.cli --all

  卡数 2 ｜ 判定 supported
  显存 权重 61.09 + KV Cache 0.61 = 需求 67.88 GiB
  并行策略 tensor_parallel
  每瓦 Token 吞吐 0.5611 token/s/W（整机 920 W / 516 token/s）
  年电费 5028.94 元（已计入部分三年 15086.82 元）
  每百万 Token 电费 1853.63 元

  形态一致性：0 条问题（P0 0 项），字段完整率 100%
```

三个场景的对比（同一张卡 S2，利用率 0.6）：

| 场景 | 模型 | 上下文 | 卡数 | 权重/KV (GiB) | 每瓦 Token 吞吐 | 每百万 Token 电费 |
|---|---|---|---|---|---|---|
| 金融 RAG | Qwen2.5-32B | 2000+500 | 2 | 61.09 / 0.61 | 0.5611 | 1853.63 元 |
| 视联网多模态 | Qwen2.5-14B | 3000+200 | 1 | 27.57 / 0.59 | 0.2532 | 4108.07 元 |
| 企业 Agent 服务 | Distill-Qwen-14B | 6000+1200 | 1 | 27.57 / 1.32 | 0.2532 | 4108.07 元 |

**并发越高，每瓦吞吐越高**（金融 RAG 60 并发 → 0.5611，
视联网 16 并发 → 0.2532）—— 这正是「每瓦 Token 吞吐」这个指标的意义：
同样的硬件，**业务并发设计直接决定单位算力成本**。
这一点在给客户做方案时比 TFLOPS 更有说服力。

## 8. 已知局限

| # | 局限 | 影响 | 补齐方式 |
|---|---|---|---|
| 1 | **吞吐基线与优化系数全是占位值** | 每瓦 Token 吞吐不可用于真实承诺 | 须用目标卡跑目标模型实测替换 |
| 2 | **无真卡实测** | 全部为理论推算 | POC 阶段补齐 |
| 3 | **加速卡单价未公开** | TCO 合计不完整 | 取得正式报价后传入 `hardware_price` |
| 4 | 电价与 PUE 为占位值 | 电费数字有偏差 | 按项目所在地实际数据替换 |
| 5 | **MoE 层占比假设影响 EP/TP 比值** | 通信量对比有偏差 | 按目标模型真实结构替换 `DEFAULT_MOE_LAYER_RATIO` |
| 6 | hidden 尺寸为占位近似 | 通信量绝对值有偏差 | 需模型的 GQA 分组倍数 |
| 7 | 目标加速卡规格多为 `unverified` | 涉目标卡的测算不确定性高 | 向厂商索取规格书 |
| 8 | 不做振动与散热的工程设计 | 只做参数一致性校验 | 需硬件团队介入 |

第 1、5、6 条是这个项目最需要盯的地方 —— **模型对不对，取决于假设准不准**。

这个工具的价值不在于给出一个数字，而在于**说清这个数字在什么假设下成立、
什么假设下会失效**：占位参数集中登记在 `data/assumptions.md`，
每份输出都带 `assumption_refs`，任何一条都可以单独替换后重算。
可复核性比数值本身重要。
